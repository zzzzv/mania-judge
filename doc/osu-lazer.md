# osu!lazer mania 规则

复刻官方 lazer 的 mania 判定与派生数据（`DrawableNote` / `DrawableHoldNote` / `Column` / `OrderedHitPolicy`）：
**按列**推进，判定时刻取回放帧，而不是连续的理想时间。实现见 `src/osu-lazer/`
（`judgement.ts` / `events.ts` / `timeline.ts` / `health.ts` / `score.ts`）。

## 判定规则

### 输入与时钟

判定的输入是每列物件（按起点升序，长条带结束时间）和平铺的回放行表（升序，一行一次推进）。

**行表就是时钟**：lazer 会把判定时钟钉在回放帧时间上，物件的结算时刻就是「边界落在的那一帧」。
行表原样透传，不去重、不排序。

真实 lazer 的 tick 比回放帧密（渲染帧 + 补偿步进），但实测在帧间插入 33.3 ~ 0.5 ms 的中间 tick
对六档计数没有任何影响，所以只按回放帧推进。

### 判定窗口

基础窗口按 OD 在 OD0 / OD5 / OD10 三点线性插值：

| 档位 | OD0 | OD5 | OD10 |
| --- | --- | --- | --- |
| Perfect | 22.4 | 19.4 | 13.9 |
| Great | 64 | 49 | 34 |
| Good | 97 | 82 | 67 |
| Ok | 127 | 112 | 97 |
| Meh | 151 | 136 | 121 |
| Miss | 188 | 173 | 158 |

「Miss」同时也是最大可命中偏移。实际窗口再乘倍速、除难度乘数，**取整后加 0.5**（小数毫秒的物件
会因此差半档，不能省）：

- 倍速（DT 1.5 / HT 0.75）由倍速 mod 写到每个物件的判定窗上，所以**倍速放大窗口**；
- 难度乘数（HR 一类 > 1）反向缩放，本库用 `windowScale` 表示它的倒数。

OD 4 的实际值：20 / 52 / 85 / 115 / 139 / 176。

**长条尾巴**把窗口放宽 1.5 倍（判定时把偏移除以 1.5，两者等价），OD 7 的尾巴是
25.8 / 64.5 / 114 / 159 / 195 / 250.5。

### 每帧的列内处理

每一列完全独立：各有自己的输入状态，以及「第一个还没判完」的游标。一帧内的顺序是
**先结算到期漏接，再派发按下 / 松开**。

这个顺序是与真实 lazer 逐物件对账后定下来的：按键落在刚过 deadline 的那一帧时，物件应该已经
被判成漏接，于是这次按键**穿透**到下一个物件。

### 单点

- 按键先过 note lock：列里下一个仍存活的物件必须还没到起点。判完的物件要等淡出结束才离开容器，
  **Miss 淡出 150ms**，这段时间里它仍然挡住前一个物件；命中（含 Meh）是瞬时移除；
- 按偏差换算档位：落在「Meh 窗之外、Miss 窗之内」判 **Miss 并消耗这次按键**；超出 Miss 窗则不判，
  按键继续传播；
- 到期漏接：偏差超过 Miss 窗即判 Miss；
- 命中后，同列**结束时间早于本物件起点**的未判物件全部被强制 Miss。

### 长条

一个长条是父物件 + 头 / 尾 / body 三个子物件。六档只算头和尾，body 与父物件产生的是 `IgnoreHit`。

- **按下**：先检查 note lock 和「尾巴是否连 Miss 窗都过了」，然后开启 holding；返回值取决于头判 ——
  头未判就按窗口判（Meh 与 Miss 之间判 Miss）并消耗这次按键，头已判（含被漏接判掉）就返回未命中，
  按键穿透到下一个物件。
- **松手**：若当前处于 holding，立刻结算尾巴（偏移除以 1.5，落在 Meh 与 Miss 之间直接判 Miss 并
  消耗这次松手），再由尾巴是否命中决定 body 是 `IgnoreHit` 还是 `ComboBreak`。**破条这一下就断连击**，
  之后重新按住并命中尾巴也撤销不了。
- **封顶**：尾巴档位高于 Meh 时，只要头没命中或 body 已破，就封顶到 Meh。
- **漏接**：头、尾、body 各自越过自己的 Miss 窗后判最小结果。

## 时间轴规则

连击、血量、六档计数与标准分都是判定完成后派生出来的。

### 事件模型

lazer 的长条是头 / 尾 / body 三个独立物件，时间轴上最多留三条事件：

| 事件 | 进档位计数 | 影响连击 | 回血 | 加分 |
| --- | --- | --- | --- | --- |
| tap 判定 | 是 | 是 | 是 | 是 |
| 长条头判定 | 是 | 是 | 是 | 是 |
| 长条尾判定 | 是 | 是 | 是 | 是 |
| 长条破条（body 的 `ComboBreak`） | 否 | **清零** | 否 | 否 |

body 平时是 `IgnoreHit`（不计分），但破条时走最小结果 `ComboBreak`，只清连击；lazer 没有 tick 事件，
长条体内不产生任何判定。破条挂在松手那一刻（不是尾巴的判定时刻），所以「松手时尾巴还没命中」
会在松手时就断连击。

### 连击

命中（Perfect / Great / Good / Ok / Meh）+1，Miss 与破条清零；最长连击在这步顺带更新。事件按
「时间 → 列号 → 物件起点」排序，同一时间戳按列从左到右处理。

### 六档计数

头和尾各产出一个可计分结果，所以一个长条贡献 2 条计数、2 次连击；tap 贡献 1 条。

### 血量

`life` 初始 1，每次判定后夹在 `[0, 1]`。lazer 的 mania **不随时间掉血**（drain 恒为 0），只按判定
档位变化：

| 档位 | 增量 |
| --- | --- |
| Perfect | (0.0055 - 当前血量 * 0.0005) * 倍率 |
| Great | (0.0050 - 当前血量 * 0.0005) * 倍率 |
| Good | (0.0040 - 当前血量 * 0.0004) * 倍率 |
| Ok | 0 |
| Meh | -(当前血量 + 1) * 0.0016 |
| Miss（头 / 尾） | -(当前血量 + 1) * 0.00375 |
| Miss（tap） | -(当前血量 + 1) * 0.0075 |

Meh 与 Miss **不乘**倍率，只有 Perfect / Great / Good 乘。倍率是 stable 遗留的 `HpMultiplierNormal`：
拿初始 drain 试跑整张谱，平均恢复量不够就放大 1% 重来，直到达标。lazer 的枚举口径没有 tick，
长条贡献「头 + 尾」两个 Perfect 增量，所以 LN 图的恢复量约是 tap 图的两倍。

**血条在 `.osr` 里是有记录的**：格式里存成 `时间|血量,` 的序列（`ScoreInfo.HealthGraph`），但写出时
只在第一个点、最后一个点、或距上一个采样超过 2000ms 时才记一个点，且时间与血量都四舍五入到两位
小数。lazer 的本地分数库里有这个字段，但 `tools/lazer-index` 为了控制体积把它排除了（fixture 的
`lifeFrames` 因此恒为空），所以目前没有可用的真值 —— 要做也只能做「每 2 秒一个点」的粗校验。

### 分数（标准分）

总分 = 150000 × 连击进度 + 850000 × 精度^(2 + 2×精度) × 精度进度，取整按中点取偶。mania 没有 bonus 项。

- 基础分：Perfect 305、Great 300、Good 200、Ok 100、Meh 50、Miss 0；
- 精度是「目前为止」的：分母只累计**已判**物件的上限分（每个 +305），所以分数会随失误回落；
- 精度进度 = 已判可计分数 / 全谱可计分数；
- 连击分贡献 = 基础分（Perfect 按 300 计）× log4(连击数) 的夹值（夹在 0.5 与 log4 400 之间）；
- 连击进度 = 当前连击分总和 / 全 Perfect 时的总和。后者不必真跑 autoplay：全 Perfect 下第 c 个
  可计分判定的连击恰为 c，直接求和即可。

算出来的是「不含 mod 的总分」。时间轴入口的第三个参数是**分数倍率**：可以直接给数字，也可以给
mod 缩写列表（按下表换算），传了就把结果折成真实总分（取整顺序与 lazer 一致：先取整、再乘倍率、
再取整）。

### mod 倍率

各 mod 的倍率**相乘**，没有组合倍率：

| mod | 倍率 |
| --- | --- |
| EZ / NF / DA / WU / WD / AS | 0.5 |
| NR / CS / HO | 0.9 |
| HT / DC | 按倍速插值：0.75 → 0.3、0.9 → 0.5 |
| 1K ~ 10K | 0.9（2025.718 之后）／1（更早） |
| CL | 0.96（旧分数版本）／1 |
| 其它（DT / NC / HR / SD / HD / CO / FL / MR / IN …） | 1 |

注意 DT / NC **没有**倍率 —— mania 的倍率表里加速那一行是注释掉的，只有减速生效。倍速插值先把
倍速截断到 0.1，再以 1.0 为基准折成倍率。历史成绩的两个开关（key mod 的 1.0 口径、Classic 的
0.96）需要客户端版本 / 记录时间 / 分数版本，不传时按当前规则算。

## 精度

### 判定：对真 lazer 逐物件

用 `tools/lazer-oracle` 跑真 lazer 的判定代码、`scripts/compare-oracle.ts` 逐物件对比（30s 片段）：

| 片段集 | 判定数 | 差异 |
| --- | --- | --- |
| 7K LN（11 段） | 9539 | 2 |
| DT 1.5x（7 段） | 5016 | 0 |
| 整谱 2 局 | 4740 | 0 |

剩下 2 处属于同一类：按键落在刚过 deadline 的同一帧，真 lazer 让它抢在漏接前把头判成 Miss 并吃掉
这次按键，本库是漏接先落地、按键穿透。已确认与 tick 密度无关，是同一帧内的时序竞争。

### 判定：对游戏内实测

用 tosu 抓游戏内播同一份回放的实时计数（`tools/tosu-verdict-capture`）：

| 来源 | 六档 | accuracy |
| --- | --- | --- |
| 游戏内 lazer 复现 | 1767 703 97 17 5 33 | 96.43308199222218 |
| 本库实现 | 1767 703 97 17 5 33 | 96.43308199222217 |
| 成绩里存的统计 | 1770 702 95 16 6 33 | 96.45371447149592 |

第三行连 lazer 自己都复现不出来：`.osr` 存的是当初游玩那一刻的判定，与用当前代码重播同一份回放
不是一回事。两者为何不同尚未查清。

### 对 `.osr` 抬头（整谱冒烟门禁）

`scripts/check-osr-stats.ts <组> [--timeline]`，分数已含 mod 倍率：

| 组 | 六档完全一致 | 偏差条数 | acc 偏差中位 / 均值 / 最大 |
| --- | --- | --- | --- |
| tap-only | 77/78 | 2（0.0012%） | 0.0000% / 0.0006% / 0.0476% |
| LN（hold） | 3/31 | 626（0.3434%） | 0.0105% / 0.0136% / 0.0586% |
| mods | 0/17 | 436（0.2974%） | 0.0083% / 0.0119% / 0.0432% |

| 组 | 最长连击一致 | 连击差 中位 / 最大 | 分数一致 | 分数差 中位 / 均值 / 最大 |
| --- | --- | --- | --- | --- |
| tap-only | 71/78 | 0 / 1 | 20/78 | 0 / 13 / 1106 |
| LN（hold） | 24/31 | 0 / 2 | 0/31 | 91 / 173 / 1741 |
| mods | 13/17 | 0 / 1 | 0/17 | -28 / 70 / 948 |

偏差形态是 Perfect 与 Great 互相抵消、Miss 基本不动，与「存的是当初那一次判定」的口径一致。
已排除的方向：tick 密度、倍速窗口缩放公式（DT 片段 0 差异）、尾巴宽松度（1.5 最优，其它档差 10 倍）、
OD（±0.2 都更差）、回放行整毫秒量化（整体平移 ±0.5ms 更差）。分数偏差远大于计数偏差，原因见最后一节。

### 时间轴：对真 lazer 的计分器与游戏内实测

- **公式**：oracle 的 dump 带真 lazer 自己的计分结果。把同一份 dump 的逐物件结果按它的应用顺序
  喂进本库公式，结果逐位相同（`Berry Go!!` 2036 条判定：两边都是 692785，accuracy 15 位相同）。
  也就是说基础分、连击项、精度分母口径都没有问题；
- **游戏内实测**：941 个采样点按「已判条数」对齐后，前约 430 条判定的分数逐点相等，末尾（全谱
  2622 条）游戏 846882、本库 846958（+76）。这条用例已经落成测试（断言前 400 条判定内逐点相等）。

## 存在的问题和原因

1. **同一帧内的时序竞争**（判定层 2/9539）。按键落在刚过 deadline 的那一帧时，谁先落地取决于
   lazer 内部的更新次序，回放数据里没有这个信息。
2. **连击分对判定落点极敏感，所以分数的残差远大于计数**。`.osr` 里六档一致 77/78，分数却只有
   20/78：
   - 分组计数看不见「一个 Miss 换了位置」（Miss 与 Great 互换后六档完全一样），但连击序列会变，
     连击分总和随之变化（单次判定约 100~300 分）；
   - 还有一种无法复现的来源是**同一帧内多条判定的应用顺序**。实测真 lazer 在「同一时间戳多列同时
     判定」时既不是列升序也不是列降序（同一张图里「列 8 先于列 6」和「列 6 先于列 8」都会出现），
     它取决于内部容器的枚举顺序。只有当同一时刻里包含 Miss 时它才影响连击分。
3. **血量只有很粗的对账口径**。`.osr` 里确实存了血条（见「血量」一节），但每 2 秒才一个采样点、
   两位小数，而且记的是当初游玩那条曲线；本地分数索引也把它排除了，所以目前仍只能按源码对齐。
   恢复倍率本身也是按「平均恢复量达标」近似，省掉了 drain 相关的两条失败分支。
4. **mod 倍率的历史口径需要成绩元数据**。key mod 的 1.0 与 Classic 的 0.96 都随客户端版本 / 分数
   版本变化，调用方不提供时就按当前规则算。
