# osu!v1（stable）时间轴逻辑

本文描述 `src/osu-v1/timeline.ts` 与 `src/osu-v1/score.ts` 里实际使用的逻辑：连击、血量、
六档计数、ScoreV1 都是**判定完成之后**再派生出来的，判定本身见
[osu-v1-mania-judgement.md](./osu-v1-mania-judgement.md)。

## 事件模型

每个物件在时间轴上最多留下三类事件：

| 事件 | 来源 | 进档位计数 | 影响连击 | 影响血量 | 影响分数 |
| --- | --- | --- | --- | --- | --- |
| `judge` | 最终判定 | 是 | 是 | 是 | 是 |
| `tick` | 长条体内 100ms 节拍 | 否 | +1 | 按 300 回血 | 否 |
| `break` | 提前松手 | 否 | 清零 | 否 | 否 |

`break` 挂在高条**提前松手的那一刻**（`breakTime`），`judge` 挂在最终判定时刻（`exit`）。
按时间排序后依次喂给同一个累加器，连击 / 血量 / 分数因此共用同一条序列。

同一时间戳的排序：先按判定产出顺序（`exit`），再按列。

## 连击

- `judge` 不是 MISS → 连击 +1；MISS → 清零
- `tick` → 连击 +1
- `break` → 清零

`maxCombo` 在这一步顺带更新。注意 tick 也进连击，所以长条谱的 `maxCombo` 会大于物件数。

## 六档计数

只有 `judge` 事件进 `resultCounts`。`tick`（值 7）和 `break`（值 -1048576）在 stable 里同样
不计数，所以这里也不计。

## 血量

血量按判定档位累加，长条的 tick 按 300 回血：

```
基础增量（hpMultiplierNormal 由谱面与回放估算）：
  MAX   +0.0055 - hp * 0.0005
  300   +0.0050 - hp * 0.0005
  200   +0.0040 - hp * 0.0004
  100    0
  50    -(hp + 1) * 0.0016
  MISS  -(hp + 1) * 0.0075
```

结果夹在 `[0, 1]`。`hpMultiplierNormal` 通过「如果全程 MAX 会回多少血」与谱面 HP drain
的比较反复放大 1%（`health.ts`）。

> `.osr` 不记录过程血条，这一层**没有真值可对照**，只能保证内部自洽。

## ScoreV1

对应 stable 的 `ManiaScoreSubmission.onJudgment`。每次判定贡献两项，再乘 `mult / 320`：

```
mult = 500000 / 物件数 * 倍率
倍率：NF / EZ / HT 各 ×0.5（HR / DT / HD / FI 不影响 base 分）
```

两项分别是：

| 档位 | 判定值 `num` | 手感权重 `w` | health 增量 |
| --- | --- | --- | --- |
| MAX | 320 | 32 | +2 |
| 300 | 300 | 32 | +1 |
| 200 | 200 | 16 | -8 |
| 100 | 100 | 8 | -24 |
| 50 | 50 | 4 | -44 |
| MISS | 0 | 0 | health 直接置 0 |

本次贡献 = `mult / 320 * (num + w * sqrt(health))`。

`health` 是这个计分器自己的量（与上面的血量条不是一回事）：

- 初始 100，夹在 `[0, 100]`；
- 每次判定**先加增量**，再判断「当前连击（加这次之前）是否为 384 的倍数」，是就覆盖回 100；
- `tick` / `break` 不改 health，但 tick 会推进连击，因此会间接影响 384 的相位。

收尾用 .NET 的 `Math.Round`（中点取偶），`999999` 特判成 `1000000`。

## 现状

| 项目 | 完全一致 | 说明 |
| --- | --- | --- |
| 最大连击 | 73 / 97 | 其余差 ±1 |
| ScoreV1 | 43 / 97 | 其余中位偏差 ±50（约 0.01%），最大 1136（0.15%） |

已知的残差特征：

- 单点谱（无 tick）分数 39/40 精确，说明公式主体（`num + w*sqrt(health)`、`unit`、取整）是对的；
- 长条谱的残差正负各半，且**与同帧排序无关**（换 4 种排序结果完全一样），说明问题出在
  health 轨迹本身，而不是事件顺序；
- 已排除的口径：用头判/尾判扣血、tick 回血、去掉 384 重置、MISS 重置 health、`sqrt` 用增量
  前的 health —— 这些都比当前写法更差。

下一步需要从 stable 的 `ManiaLongNote` 计分侧拿到 health 的完整写入路径，或者拿到逐物件的
判定真值。
