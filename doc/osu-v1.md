# osu!v1（stable）mania 规则

复刻 osu!stable 的 mania 判定与派生数据：**按列**推进，判定时刻取回放帧，而不是连续的理想时间。
实现见 `src/osu-v1/`（`judgement.ts` / `timeline.ts` / `health.ts` / `score.ts`）。

## 判定规则

### 输入与时钟

判定只需要两样东西（都在 `OsuData` 里）：

| 字段 | 内容 |
| --- | --- |
| `noteColumns` | 每列的物件，按起点升序；长条额外带结束时间 |
| `frames` | 回放原始行表：时间 + 该帧按下的列，升序，一行一次推进 |

**行表就是时钟。** stable 逐帧推进，物件的结算时刻就是「边界落在的那一帧」。行表原样透传，
不做折叠、不去重、不排序。

### 判定窗口

基础窗口由 OD 线性决定：

| 档位 | OD0 | OD5 | OD10 |
| --- | --- | --- | --- |
| MAX | 16 | 16 | 16 |
| 300 | 64 | 49 | 34 |
| 200 | 97 | 82 | 67 |
| 100 | 127 | 112 | 97 |
| 50 | 151 | 136 | 121 |
| 到期 | 188 | 173 | 158 |

「到期」同时也是最大提前输入距离。实际窗口再乘 `speedRate * windowScale`（DT / HT 与 HR / EZ 的
作用），**乘完向下取整** —— stable 的窗口是整数，缩放之后同样取整。

### 每帧的列内处理

每一列完全独立：有自己的输入状态、自己的物件游标。每帧的顺序固定：

1. 更新这一列的「本帧是否按下」「上一帧是否按下」；
2. 清空本帧的「已消费」标记（一帧一列最多消费一个物件）；
3. 从游标处开始扫描该列尚未完结的物件。

扫描时按顺序判断：

| 情况 | 处理 |
| --- | --- |
| 已判定且起点在当前时间之后 | **封锁整列**（后面的物件本帧都不再处理） |
| 本帧该列已被消费 | 跳过 |
| 还没进入判定范围 | 跳过 |
| 越过「结束 + 100 窗」 | 到期结算：未判定的直接判（正常就是 MISS） |
| 新按下边沿 | 单点：记按下并判定；长条：记按下、判头、开始算 tick |
| 持续按住 | 只对长条生效：推进 tick |
| 已松开 | 长条且正按着 → 结算；其余情况等待变暗后结算 |

到期检查排在任何按键处理之前，这是 stable 的顺序 —— **先结算再过边沿**。

### 单点

按下时用「按下时刻与起点的偏差」依次对照 MAX / 300 / 200 / 100 / 50 窗口，命中第一个满足的档位；
都没命中就是 MISS。到期仍未按下也是 MISS。

### 长条（头尾合并）

V1 的长条只产生**一个**判定，用头和尾的合成误差决定档位。先算两个「有效时刻」：

| 按下情况 | 有效按下时刻 |
| --- | --- |
| 早于「起点 - 50 窗」 | 结束 - 1（早得离谱，等于没按头） |
| 早于起点 | 起点 + (起点 - 按下)（按镜像算） |
| 其余 | 按下时刻 |

| 松手情况 | 有效松手时刻 |
| --- | --- |
| 仍按住 | 当前帧时间 |
| 晚于结束 | 结束 - (松手 - 结束)（按镜像算） |
| 其余 | 松手时刻 |

记头误差 = 有效按下与起点的差、尾误差 = 有效松手与结束的差，合成误差为两者之和：

| 档位 | 条件 |
| --- | --- |
| MISS | 有效松手早于「结束 - 50 窗」（尾部根本没按住） |
| MAX | 头误差在 MAX 窗的 1.2 倍内，且合成误差在 MAX 窗的 2.4 倍内 |
| 300 | 头误差在 300 窗的 1.1 倍内，且合成误差在其 2.2 倍内 |
| 200 | 头误差、合成误差分别在 200 窗的 1 倍 / 2 倍内 |
| 100 | 头误差、合成误差分别在 100 窗的 1 倍 / 2 倍内 |
| 50 | 其余 |

**破条封顶 200**：只要在「结束 - 50 窗」之前松过手，最终判定最高只能是 200。

三个守卫决定「什么时候才允许写判定」：还没到「起点 + 50 窗」且从未按下就不判；还没到
「结束 - 50 窗」时，正按着就继续等，已经松开则记一次 break 且**不写判定**（之后可以再按回来）；
还按着且没到「结束 + 50 窗」也继续等。break 不是判定：不进六档计数，只在时间轴上清连击。

长条按住时还会每 100ms 产生一个 **tick**：网格从按下时刻起算，每次只前进一格（不是重置成当前
时间）；只加连击和血量，不进六档计数、不加分。

### 变暗与结算

越过「起点 + 50 窗」仍未按住、未判定的物件会变暗。变暗之后不再自动结算，等玩家有输入时再看
（松手会触发结算，按下会重新接上）。

回放结束后仍未判定的物件按「结束 + 100 窗、结束 + 50 窗 + 1ms、起点 + 50 窗 + 1ms 三者取大」补判。
补判出来的 MISS，判定时刻**回填到变暗那一帧** —— stable 是在变暗时就把它判死的，不回填会让所有
漏接挤到回放结尾，连击断点全错。

## 时间轴规则

连击、血量、六档计数、ScoreV1 都是判定完成后派生出来的。

### 事件模型

每个物件在时间轴上最多留下三类事件：

| 事件 | 来源 | 进档位计数 | 影响连击 | 影响血量 | 影响分数 |
| --- | --- | --- | --- | --- | --- |
| judge | 最终判定 | 是 | 是 | 是 | 是 |
| tick | 长条体内 100ms 节拍 | 否 | +1 | 按 300 回血 | 否 |
| break | 提前松手 | 否 | 清零 | 否 | 否 |

break 挂在提前松手的那一刻，judge 挂在最终判定时刻；按时间排序后依次喂给同一个累加器，连击 /
血量 / 分数因此共用同一条序列。同一时间戳先按判定产出顺序，再按列。

### 连击

判定不是 MISS → +1；MISS → 清零；tick → +1；break → 清零。最长连击在这步顺带更新。注意 tick
也进连击，所以长条谱的最长连击会大于物件数。

### 六档计数

只有 judge 进计数。tick 与 break 在 stable 里同样不计数，所以这里也不计。

### 血量

`life` 初始 1，每次判定后夹在 `[0, 1]`，tick 按 300 回血：

| 档位 | 增量 |
| --- | --- |
| MAX | +0.0055 - 当前血量 * 0.0005 |
| 300 | +0.0050 - 当前血量 * 0.0005 |
| 200 | +0.0040 - 当前血量 * 0.0004 |
| 100 | 0 |
| 50 | -(当前血量 + 1) * 0.0016 |
| MISS | -(当前血量 + 1) * 0.0075 |

公式里的倍率（`hpMultiplierNormal`）由「如果全程 MAX 会回多少血」与谱面 HP drain 的比较反复放大
1% 估出来。

**血条在 `.osr` 里是有记录的**：格式里存成 `时间|血量,` 的序列，但写出时只在第一个点、最后一个点、
或距上一个采样超过 2000ms 时才记一个点，且时间与血量都四舍五入到两位小数。所以它只能当粗校验
（整张谱几十个点），不足以做逐帧对账；本库的解析链（osu-mania-io）目前也没有暴露这个字段。

### 分数（ScoreV1）

每次判定贡献两项，再乘「单价」：单价 = 500000 / 物件数 × 分数倍率；分数倍率只受 NF / EZ / HT
影响（各 ×0.5，`v1.scoreMultiplier` 就是这张表），HR / DT / HD / FI 不影响基础分。时间轴入口的
第三个参数也是这个倍率，直接给数字或给 mod 缩写列表都行。两项分别是「判定值」与「手感权重 ×
根号 health」，相加后除以 320。

| 档位 | 判定值 | 手感权重 | health 增量 |
| --- | --- | --- | --- |
| MAX | 320 | 32 | +2 |
| 300 | 300 | 32 | +1 |
| 200 | 200 | 16 | -8 |
| 100 | 100 | 8 | -24 |
| 50 | 50 | 4 | -44 |
| MISS | 0 | 0 | health 直接置 0 |

这里的 health 是这个计分器自己的量，与上面的血条不是一回事：初始 100、夹在 `[0, 100]`；每次判定
先加增量，再看「加这次之前」的连击是否为 384 的倍数，是就把 health 覆盖回 100。tick 与 break
不改 health，但 tick 会推进连击，因此间接影响 384 的相位。收尾按中点取偶取整，999999 特判成
1000000。

## 精度

### 对 `.osr` 抬头

97 张样本（7K–18K，含 NM / EZ / HR / DT / HT），`.osr` 抬头是回放自带的统计：

| 项目 | 完全一致 | 残差 |
| --- | --- | --- |
| 六档计数 | 94/97 | 3 张各差 2 个事件（一升一降，净 0） |
| 最长连击 | 90/97 | 差 1–5 |
| ScoreV1 | 47/97 | 单点谱 39/40 精确；长条谱中位差 51、最大 1136 |

单点谱能精确到 39/40，说明公式主体（判定值 + 手感权重、单价、取整）是对的。长条谱的残差正负各半，
且**与同帧排序无关**（换 4 种排序结果完全一样），说明问题出在 health 轨迹本身而不是事件顺序。
已排除的口径：用头判 / 尾判扣血、tick 回血、去掉 384 重置、MISS 重置 health、根号用增量前的
health —— 这些都比当前写法更差。

### stable 自己也复现不出 `.osr` 抬头

这 3 张残差不是本实现对 stable 的偏差，而是 **stable「播放回放」与「当初游玩」的差异**。抬头记的是
当初游玩那一刻的判定，而 stable 播回放时会按当前帧重新判定，两者本来就不保证相同。

`Life is Piano` 7K（1473 物件 / 572 长条，无 mod）做过整图实测：

| 输入 | Perfect | Great | Good | Ok | Meh | Miss | maxCombo |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 成绩里存的统计（`.osr` 抬头） | 783 | 508 | 138 | 25 | 8 | 11 | 1494 |
| 本库（原始回放文件） | 783 | 508 | 138 | 25 | 8 | 11 | 1494 |
| 本库（验证用的那份回放文件） | 783 | 508 | 138 | 26 | 8 | 10 | 1494 |
| 游戏内重放同一份回放（tosu 抓取） | 783 | 508 | 138 | 26 | 8 | 10 | 1494 |

同一份成绩的两条回放记录，只有一次按键落在帧边界前后之一，就有一个物件在 100 与 MISS 之间翻转；
本库跟着回放帧走，因此与「游戏内重放」逐档一致，而与抬头差一格。结论：**`.osr` 抬头不能当作判定
正确性的基准**，只能当近似门禁。

出处：前两行与第三行可以用本地样本随时复现（`Life is Piano-7K SHD-94.55` 与
`MJVerify 7 Life is Piano-Seg30 7K SHD-94.55`），第四行是 2026-11-16 用 tosu 抓的一次记录 ——
抓取文件不入库，要复核得自己开游戏播这份回放（`pnpm tosu:capture`）。

## 存在的问题和原因

1. **长条谱的 ScoreV1 残差**（中位 51 分、最大 1136）。健康值（health）的写入路径只掌握了一部分，
   缺少 stable 的 `ManiaLongNote` 计分侧完整实现，也拿不到逐物件的判定真值 —— stable 是闭源二进制
   （没有可对照的执行环境），所以这一项只能靠源码语义推。下一步需要拿到 health 的完整写入路径。
2. **连击差 1–5 与分数残差同源**。最长连击完全一致 90/97，差的 7 张都集中在长条谱，
   差异是 tick 与破条的落点漂移，判定档位本身没变。
3. **血量只有很粗的对账口径**。`.osr` 里确实存了血条（见「血量」一节），但只有每 2 秒一个采样点、
   两位小数，而且记的是当初游玩那条曲线；解析链目前也没有把它带进来。所以血量只能按源码对齐，
   无法做逐帧验证。
